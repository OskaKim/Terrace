# 0015 公式のサーバーは置かず、遊ぶ人がサーバーを立てる。ゲームから開くワールドは、同梱の Server を子プロセスで起動する

- 日付: 2026-11-04

## 背景

MMO に近い遊び心地(知らない人とも同じマップで狩る、積み上げが残る)にしたい。ただし公式のサーバーを置くと、人が増えるほど費用が増え、落ちたときの対応・不正への対処・問い合わせの手間も持つ。

手本の Palworld は、公式のサーバーを置かず、遊ぶ人が立てたサーバーで遊ばせている。形は 2 つある。ゲームの中から自分のワールドを開いて友達を呼ぶ形と、配られたサーバーを自分の PC や借りたサーバーで立てる形(専用サーバー)。

今の作りは、この形と相性が良い。

- サーバーは 1 プロセスで完結し、DB も外のサービスも使わない
- Linux の Docker の像がある([ADR 0011](0011-server-in-docker.md))
- Client のログイン窓には接続先を入れられる。LAN の中なら、今でも `TerraceServerOptions.ListenAnyIP` で遊べる

一方で、MagicOnion のサーバーは ASP.NET Core の上で動き、Unity(Mono / IL2CPP)の中では動かない。

## 決定

### 遊ばせ方

- 公式のサーバーは置かない。遊ぶ人がサーバーを立て、ほかの人はゲームの中で接続先を入れて入る
- 主な形は「ゲームから開くワールド」。遊ぶ人(持ち主)がゲームの中から自分のワールドを開き、接続先を友達に伝える。持ち主がゲームを閉じると、ワールドも閉じる
- もう 1 つの形は「専用サーバー」。配ったサーバーを、遊ぶ人が自分の PC や借りたサーバーで立てる。いつも立っていて、知らない人も出入りする
- 操作はゲームの中だけで済ませる(シェルスクリプトなどを別に実行させない)。持ち主の回線が外からの接続を受けられるかは、ゲームでは変えられない。届かないときは、理由の候補を出すところまでにする

### サーバーの置き方

- サーバーの実装は `Terrace.Server` の 1 つだけにする。ゲームから開くワールドでは、Client が同梱した `Terrace.Server` を子プロセスで起動し、持ち主の Client も `localhost` に繋ぐ。持ち主の Client は「ただの 1 人」で、特別な権威を持たない
- Unity の中に、別の通信で 2 つ目のサーバーを作らない
- 子プロセスには、ワールドのフォルダ・ポート・外からの接続を受けるか・親のプロセスを、起動引数で渡す。親のプロセスがいなくなったら、サーバーは保存してから終わる
- 専用サーバーは、同じ `Terrace.Server` を、自己完結の版と Docker の像で配る

### キャラクターと本人確認

- キャラクターと持ち物は、ワールド(サーバー)ごとのセーブに入る。友達のワールドごとに別のキャラクターになる。サーバーをまたいで持ち込まない
- 本人確認は、ワールドごとのトークンで行う。初めて入るワールドで Server がトークンを発行し、Client はワールドの ID ごとに保存する。次からはそのトークンで、同じキャラクターに戻る。名前とパスワードのアカウントは持たない
- ワールドの ID は、サーバーがワールドを初めて作るときに決める(接続先のアドレスは変わることがあるため)
- ワールドに入るには、持ち主が決めた合言葉を求められる(持ち主が合言葉を決めていなければ要らない)
- 版が違えば入れない。持ち主のゲームに入っているサーバーの版が基準になる

### ひとりで遊ぶ

- ひとりで遊ぶのも「誰も呼ばないワールド」にする。ひとりのときは `localhost` だけで待ち、あとから外の接続を受けるようにすれば、そのままマルチになる
- 移った後は、Client の `OfflineRoom` と、オフラインで規則を決める係(敵・ドロップ・撃破の報酬など)を消す。ゲームの規則は Server の `Room` の 1 か所にだけ置く
- 移るまでの間も、新しい規則は Server にだけ書き、Client のオフラインの側には足さない
- Unity のエディタで遊ぶときも、同じ仕組みで Server を立てる

### 切れたとき

- 切れたら「繋ぎ直す / タイトルへ戻る」を選ばせる。その場でひとり遊びに切り替える形はやめる

### 段階

| 段階 | 遊び方 | 外に要るもの |
|---|---|---|
| 1. ゲームから開くワールド | 持ち主が接続先と合言葉を伝え、友達がゲームの中で入れる。ひとり遊びもここに移す | 無し |
| 2. いつも開いておく | ゲームを描画しない「ワールドの番だけする」形で起動する。専用サーバーを配る | 無し |
| 3. どの回線でも入れる | プラットフォームの P2P と中継で NAT を越える | プラットフォームの SDK |
| 4. サーバーの一覧(任意) | 公開のサーバーを一覧から選ぶ | 一覧の置き場 |

- 段階 1 の前に、ログインの形(ワールドの ID・トークン・合言葉・版)を決める。[ADR 0014](0014-player-state-server-authority.md) の段階 1(セッション)と、版の握手を、この形で行う
- 段階 1 では、ワールドのフォルダへの保存も要る。持ち主の PC が全員分を持つので、自動のバックアップも要る
- 段階 1 の最初に、Smart App Control を有効にした Windows で、同梱したサーバーが起動するかを確かめる

## 理由

- 運営費も、落ちたときの手間も、立てた人の側に移る
- サーバーを 1 つにすれば、権威の形・通信・Client の Core を変えずに済む。Unity の中に 2 つ目のサーバーを作ると、通信が 2 系統になり、Hub と同じ橋渡しを Unity にも書くことになる
- キャラクターを Client に持たせて持ち込めるようにすると、Client が改ざんし放題になる。サーバーの持ち主は自分の世界を何とでもできるので、サーバーをまたぐ値は信用できない。ワールドごとにすれば、プレイヤーの状態を Server 権威へ移す向き([ADR 0014](0014-player-state-server-authority.md))とも揃う
- 中央が無いので、アカウントを公式には持てない。ワールドごとのトークンなら登録が要らず、漏れても、そのワールドの分だけで済む
- ひとり遊びも同じ形にすれば、規則が 1 か所になる。今は敵とドロップの規則が Client と Server の 2 か所に手書きであり、既にずれている。2 か所を揃え続けるより、1 か所にする方が安い。ひとりのときの進み具合も、同じセーブに残る
- 切れたらひとり遊びに切り替える形では、切れた後に進めた分がどこにも保存されず、ワールドにも戻せない

## 引き換えにしたもの

- 配布が大きくなる(.NET の実行環境ごと同梱する)。ワールドを開くとき、プロセスの起動を待つ
- 子プロセスの形は PC だけ。スマホや WebGL に出すなら、開く側には使えない
- ネット越しに届くかは、持ち主の回線しだい(NAT、IPv4 over IPv6)。どの回線でも入れるのは段階 3 まで待つ
- 段階 2 までは、持ち主がいないと遊べない。持ち主の PC が壊れると、全員分のキャラクターが消える
- 持ち主は自分のワールドで何でもできる(セーブも規則も書き換えられる)。サーバーをまたぐ順位・取引・フレンドは持てない
- トークンを失うと、キャラクターに戻れない。PC を替えるときの書き出しは後で足す
- 接続先を伝えると、持ち主の IP アドレスが友達に分かる
- Unity のエディタで遊ぶにも、PlayMode の試験にも Server が要る。開発する PC で Smart App Control に止められるときは、Docker で立てる([ADR 0011](0011-server-in-docker.md))
- ひとり遊びが移るまで、新しい規則はオンラインでだけ働く
- 遊ぶ人の PC で、署名の無いサーバーが Smart App Control に止められうる。コード署名にお金をかけるかは、段階 1 の最初に確かめてから決める
